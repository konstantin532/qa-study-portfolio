Цель этапа

Добавь матрицу прослеживаемости:

Требование → тест-кейс → результат → дефект.

Модель связей

Поддержи следующие отношения:

— одно требование связано с несколькими тест-кейсами;
— один тест-кейс связан с несколькими требованиями;
— тест-кейс имеет результаты в разных прогонах;
— результат может быть связан с несколькими дефектами;
— дефект может затрагивать несколько тест-кейсов или требований.

Используй стабильные идентификаторы. Не используй названия, индексы массива или положение элемента как ключ связи.

Если существующая модель хранит отношения одновременно в нескольких местах, выбери один источник истины либо реализуй строго синхронизируемые индексы. Не оставляй две несогласованные версии одной связи.

Модель требования

Требование должно поддерживать:

— воспроизведи;
— исправь;
— добавь регрессионный тест;
— повторно запусти;
— обнови статус.

Quality gate этапа A

Этап A пройден, если:

— нет открытых Blocker;
— нет необработанных Critical;
— основные пользовательские данные сохраняются;
— импорт не уничтожает корректные данные;
— обязательные браузеры либо проверены, либо честно обозначены Blocked;
— нет критических нарушений Axe;
— нет неподтверждённого CI Passed.

Этап B — доказательства QA-навыков

Проверь хотя бы один связный проект QA Study Portfolio.

Он должен содержать:

— требования;
— чек-лист;
— тест-кейсы;
— техники тест-дизайна;
— тестовые данные;
— тест-план;
— тестовый прогон;
— результаты;
— дефекты;
— матрицу покрытия;
— автоматические тесты;
— итоговое заключение;
— историю исправленных дефектов.

Не создавай сотни элементов. Подготовь небольшой, но связный набор.

Каждый результат должен иметь происхождение:

— manual;
— automated;
— imported;
— template;
— prepared;
— not run.

Не заменяй отсутствие результата фиктивным Passed.

Баг-репорт должен содержать:

— идентификатор;
— заголовок;
— окружение;
— предусловия;
— шаги;
— ожидаемый результат;
— фактический результат;
— severity;
— priority;
— статус;
— требование;
— тест-кейс;
— прогон;
— исправление;
— регрессионную проверку;
— ссылку на commit только при её наличии.

История дефекта должна показывать:

Обнаружение → регистрация → анализ → исправление → повторная проверка → регрессия → закрытие.

Quality gate этапа B

Этап B пройден, если работодатель может открыть один проект и проследить весь QA-цикл без перехода к несвязанным демонстрационным данным.

Этап C — учебная программа

Проверь направления:

— Web и DevTools;
— API и Postman;
— SQL;
— Mobile;
— Git;
— Bash;
— процесс тестирования;
— автоматизация;
— подготовка к собеседованию.

Для каждого направления должны быть:

— краткое собственное описание;
— статус;
— практический материал;
— связанный проект или артефакт;
— следующий шаг;
— источник, если использовался;
— отсутствие скопированного контента.

— собственные заметки;
— практические задания;
— связи с проектом;
— статус подготовки.

Не создавай ложные ответы о коммерческом опыте.

Страница дорожной карты релиза

Прогресс рассчитывай по задачам. Blocked не считай выполненным.

Проверка восстановления

Перед релизом отдельно проверь:

— экспорт текущих данных;
— очистку состояния;
— импорт собственного экспорта;
— сохранение количества основных сущностей;
— сохранение связей;
— сохранение прогонов и snapshots;
— отсутствие секретов;
— восстановление после неудачного импорта;
— возможность отменить разрушительную операцию.

Финальные команды

Запусти все реально существующие команды:

— чистую установку зависимостей;
— production build;
— static;
— syntax;
— security;
— Playwright Chromium desktop;
— Playwright Chromium mobile;
— Playwright Firefox;
— Axe;
— дополнительные проверки SQL и Postman, если они настроены.

Не удаляй тест и не ослабляй важное ожидание только ради зелёного результата.

Если команда не существует, не выдумывай её успешный запуск. Укажи NotApplicable или NotRun с объяснением.

Итоговый статус релиза

Используй только один вариант:

— Ready;
— Ready with known limitations;
— Not Ready.

Ready:

— все обязательные проверки выполнены;
— нет Blocker и Critical;
— восстановление данных подтверждено;
— поддерживаемые браузеры проверены;
— CI подтверждён либо не является обязательным и это указано.

Ready with known limitations:

— обязательные проверки пройдены;
— остались документированные неблокирующие ограничения.

Not Ready:

— есть Blocker или Critical;
— обязательная проверка упала;
— данные могут потеряться;
— импорт или экспорт ненадёжен;
— обязательный браузер не проверен без согласованного исключения;
— релизный CI не подтверждён, хотя заявлен как обязательный.

Release-readiness-отчёт

Предоставь:

1. Исходное состояние.
2. Изменения текущего этапа.
3. Статус каждой задачи этапа A.
4. Доказательства этапа B.
5. Состояние направлений этапа C.
6. Реестр дефектов.
7. Исправленные дефекты.
8. Открытые риски.
9. Изменённые файлы.
10. Миграции.
11. Тесты.
12. Фактически запущенные команды.
13. Результаты каждого браузера.
14. Результаты Axe.
15. Результаты static, syntax и security.
16. Проверку GitHub Pages.
17. Проверку экспорта и восстановления.
18. Неподтверждённые проверки.
19. Известные ограничения.
20. Итоговый статус релиза и его обоснование.

Главный результат — стабильное и честное QA-портфолио, в котором прослеживается полный цикл:

требование → техника тест-дизайна → тест-кейс → прогон → результат → дефект → исправление → регрессионная проверка → итоговое заключение.

Не объявляй проект готовым автоматически. Решение должно основываться только на фактических доказательствах.
